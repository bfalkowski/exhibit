Exhibit

Every pull request brings its own evidence. Exhibit decides what evidence a PR needs, checks that the evidence is strong, and learns from each bug that gets through.

  • A CLI that CI runs on every PR, and that a session can run before it opens one.
  • It learns its rules from your own PR history, not from guesses.
  • It tells you, with numbers, when you can stop reading the code for one kind of change.

01

Trust moves from the code to the checks

Today a person reads the diff and decides. Exhibit asks a different question: is the evidence strong enough that nobody needs to read the code? To answer it, you measure the checks, not the code.

02

One loop with two halves

The top half learns from history. The bottom half checks each new PR. When a bug gets through anyway, it goes back into the top half, and the policy gets better.

03

Learn from the bugs that got through

  1. Export each merged PR: its files, reviews, CI results, and the evidence section of its body.
  2. Trace each fix back to the PR that added the bug (Figure 3).
  3. Do error analysis. Claude drafts a short code for each escaped bug, you confirm or fix it, and the codes group into categories.
  4. Turn each category into a rule for a kind of change.

04

What happens on each PR

The rules live in the repo as evidence.yml. Changing a rule is a PR like any other, and you review it, because the quality bar stays with you.

# evidence.yml: what each kind of change must show
version: 3
kinds:
  relay-core:
    match: [relay/supervisor.js, relay/session-host.js]
    risk: high
    needs: [tests-before-after, restart-run, mutation: 0.85]
    merge_without_reading: never
  office-visual:
    match: ["office/**/*.js", "office/**/*.css"]
    needs: [tests-before-after, screenshot]
  ticket-store:
    match: ["relay/ticket-stores/**"]
    needs: [contract-test, mutation: 0.80]
  manual:
    match: ["docs/manual/**"]
    needs: [link-check, plain-words]
    merge_without_reading: allowed    # step 3 for this kind
default:
  needs: [tests-before-after, mutation: 0.70]
05

Tests that pass are not enough

A weak test passes too. To measure the tests, Exhibit plants small bugs in the lines the PR changed and checks that the tests fail. It is the same idea as injecting faults into an agent run, applied to code.

Exhibit also records who wrote each check. A test the builder wrote can share the builder's blind spots. A hidden suite that the builder cannot see counts for more.

06

A CLI that CI runs

Each PR's evidence.json goes into the check's output and onto a data branch. The history is rebuilt from git and the GitHub API, so anyone can run it on their own repo.

08

When can you stop reading the code?

For one kind of change at a time, and only when the numbers say so. The biggest step is from 2 to 3. If a check misses nothing in n PRs, the 95% upper bound on its miss rate is about 3 divided by n. That is the rule of three.

09

How the office builds, uses and tests it

Use

  • Each session runs exhibit check before it opens a PR. CI runs it again.
  • The evidence section of the PR body comes from the exhibit, not from memory.
  • Reviewer sessions read evidence.json first and spend their time on the gaps.
  • The merge rung reads the verdict, in shadow mode first.

Test

  • Each new fix is traced back. A bug the exhibit did not flag is a policy miss.
  • Planted-fault PRs must be flagged. They are labeled and never merge.
  • The same commit checked twice gives the same result.
  • Claims are checked again, for example "this test failed on the base".
  • When a session fights the tool, it files a ticket.

Iterate

  • Room C ships releases. The other rooms upgrade and confirm their fixes.
  • Room B enforces the verdict while Building58 stays in shadow mode, so you can compare them.
  • A weekly field log tracks misses, false demands, the time each check adds, and tokens per merged PR.
10

Limits

  • SZZ is noisy. Refactors, moved code and whitespace changes make false links. Exhibit shows each link with its evidence, and a person can reject it.
  • Bugs nobody noticed are invisible. History only shows bugs that someone fixed. The blind sample of merged PRs is how you find the rest.
  • A small history gives wide intervals. About 100 PRs is enough for error analysis, but not for confident rates. The rooms add more every day.
  • Mutation testing is slow. Exhibit limits it to the changed lines and gives it a time budget.
  • A policy belongs to one repo. Rules from Building58 may not carry over to edd-platform. Two repos let you test that early.
  • One model writes the code and the fixes. Expect shared blind spots. Hidden checks and your sample are the defense.

Words used on this page

Escaped defect
A bug that got through review, merged, and was found and fixed later.
SZZ
A method that traces a fix back to the change that added the bug, with git blame on the lines the fix touched.
Error analysis
Read the failures, give each a short code, then group the codes into categories.
Mutant
A copy of the code with one small change planted on purpose, such as > made into >=.
Catch rate
The share of mutants that make the tests fail. It is the TPR of the tests for this change.
TPR
True positive rate. Of the things a check should catch, the share it does catch.
Policy miss
An escaped defect whose PR the exhibit did not flag.
False demand
Evidence the policy asked for on a PR that turned out to be fine. It is the cost of the policy.
Shadow mode
Exhibit gives its verdict, but nothing waits on it.
Blind sample
Merged PRs picked at random that you read without seeing the verdict first.
Rung
One step on the trust ladder, for one kind of change. Only you turn a rung on.
